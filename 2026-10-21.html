Notion AI 에이전트 리빌드… Auto 라우터 + 크레딧제
webpronews · technobezz · Notion 공식 블로그 (10월 19일)

Notion이 AI 에이전트를 전면 재구축했다. 6세대 하네스는 세션마다 전용 서비스 + 큐 기반 워커 루프 구조로, 재시작을 버티고 단일 작업을 24시간까지 끌고 간다. 기존 상한은 5분이었다.

에이전트는 자기 컴퓨터와 브라우저를 갖는다. 토큰으로 때우던 일을 짧은 스크립트로 코드 실행한다. 긴 대화는 각 제공자의 네이티브 컴팩션으로 압축하고, 큰 툴 결과는 컨텍스트 밖으로 오프로드한다. "Review for me" 모드는 별도 모델이 행동 전 안전성을 검사한다. 웹·모바일에서 최대 50% 빨라졌고, 가동률 99.9% 이상, Custom Agent 실행 비용은 테스트에서 약 30% 감소했다.

핵심 수치
단일 작업 지속5분 → 24시간+
Auto 라우터 (Opus 5.5급 품질)비용 약 90%↓
크레딧 (시트당/월)1,500 + 500

과금도 바뀌었다. Business·Enterprise 시트당 월 1,500 Standard 크레딧(Notion이 모델 선택) + 500 Select 크레딧(사용자가 모델 선택·Custom Agent). 신규 고객은 즉시, 기존 고객은 11월 2일 전환. ChatGPT 구독 연결, 기업용 BYOK 프라이빗 알파, MCP 서버 개편, 관리자용 AI Command Center 프리뷰도 함께 나왔다.

🔧 하네스 관점
6세대 하네스의 설계(큐 기반 워커 루프·컨텍스트 컴팩션·대용량 결과 오프로드)는 장기 실행 에이전트의 정석 패턴이다. "Review for me"(별도 모델의 사전 안전 검사)는 네 듀얼 검수와 같은 발상. 네 하네스에 장기 세션 개념을 넣는다면 이 구조가 레퍼런스가 된다.

볼 포인트 ─ 11월 2일 전환 후 실제 크레딧 소진 속도, Auto 라우터의 독립 검증.

JetBrains Air EAP… IDE 5종에 에이전트 오케스트레이션
tech-insider (10월 20일) · daily.dev

JetBrains가 IDE용 Air의 EAP(앞서 해보기)를 열었다. IntelliJ IDEA·PyCharm·WebStorm·CLion·RustRover 5종, 2026.2 이상에서 플러그인으로, 2026.3 EAP 빌드에는 네이티브로 들어간다.

핵심은 "오케스트레이션이지 모델이 아니다"라는 포지셔닝이다. Air는 AI 제공자가 아니라 통로다. Codex·Gemini·GitHub Copilot·Claude Agent·Junie를 표준 지원하고, ACP 프로토콜로 Cursor 등도 붙는다. 에이전트 없이 출하되며, 사용자가 에이전트에 로그인하기 전에는 어떤 데이터도 나가지 않는다. 여러 에이전트 세션을 병렬로 돌리며 진행 상황·비용·차분·워크트리를 한 화면에서 본다. 무료 Junie Lite로 체험 가능하다.

JetBrains의 기존 AI Assistant(채팅 중심)와도 선을 그었다. "여러 작업을 동시에 지휘하는 건 대화와 근본적으로 다르다"는 것. 세션은 에디터 탭으로 열리고, Ctrl 두 번이면 현재 컨텍스트를 붙인 프롬프트 창이 뜬다.

🔧 하네스 관점
"오케스트레이션이 모델이 아니다" — 네 opencodex 합의(하네스가 루프를 정하고 모델은 생각만)와 같은 선언이다. ACP 같은 개방형 프로토콜에 거는 것도 주목할 만하다. 네 하네스의 리뷰어 호출 규약을 ACP 형태로 문서화해두면 이 생태계와 맞물릴 여지가 생긴다.

볼 포인트 ─ EAP 피드백 반영 속도, 정식 출시 시점(미정).

Self-HPO… 에이전트가 자기 하네스를 고쳐 +7점
explainx.ai (10월 19일) · Microsoft Research + UVA + CMU

Microsoft Research가 에이전트가 자기 하네스를 직접 다시 쓰고, 그 하네스 안에서 RL로 모델을 훈련하는 방법 Self-HPO를 공개했다. 베이스는 오픈 모델 Qwen3.5-35B-A3B, 시드 하네스는 mini-SWE-agent.

SWE-bench 3종(Verified·Multilingual·Pro) 평균 해결률이 57.8%에서 64.8%로 올랐다. 더 강한 교사 모델은 필요 없었다. Claude Opus 4.8을 하네스 작성자로 써도 Verified에서 +2.1점에 그쳤다. 논문·코드·하네스·체크포인트가 전부 공개됐고 체크포인트는 Apache-2.0이다.

핵심 수치
SWE-bench 3종 평균57.8% → 64.8%
교사 모델 필요없음
베이스 모델Qwen3.5-35B-A3B

단, 수치는 저자 자체 측정이고 단일 베이스 모델·Python 태스크 한정이다. 그럼에도 "하네스가 제품"이라는 명제를 재현 가능한 형태로 증명한 사례다. 어제 Harness²의 refinement와 같은 궤적 — 하네스↔정책을 교대로 개선하는 루프가 연구의 주류가 되고 있다.

🔧 하네스 관점
네 하네스에 바로 빌릴 패턴이다. 검수 결과를 모아 프롬프트·스크립트를 고치는 refinement pass를 주기적으로 돌리는 것. Self-HPO가 공개한 하네스 진화 로그를 보면 어떤 종류의 수정이 점수를 올리는지 힌트가 있다. 다만 네 하네스는 검수 기준이 명확한 쪽이라, 오히려 refinement 품질을 높이기 쉬운 구조다.

볼 포인트 ─ 공개 하네스의 실제 재현 결과, Python 외 언어 확장 여부.

EXANTE Codey… 6개 에이전트, 250건 중 75% 무인 완료
fintech.global (10월 16일)

투자사 EXANTE가 6개월간 사내에 심은 자율 개발 시스템 Codey의 성적표를 공개했다. Jira 티켓에서 동작하는 기능까지 인간 개입을 최소화하고 간다. 250건 중 75%가 무인으로 완료됐고, 도입 팀 전체 작업의 7%를 처리한다. 코딩 시작부터 배포된 기능 환경까지 약 30분이다.

Claude Agent SDK·Codex·OpenCode 위에서 돌아가며, researcher·planner·developer·reviewer·QA tester·verifier 6개 전문 에이전트를 둔다. 역할마다 다른 모델을 붙이고, 리뷰어·자동 검사가 걸면 수정으로 돌려보낸다. 스프린트 계획이나 Slack으로 작업이 들어오면 요구사항을 정리해 Jira 티켓을 만들고, MR과 프리뷰 링크로 돌아온다.

EXANTE의 결론이 뼈아프다. "진짜 병목은 모델 성능이 아니라 조직의 규율"이었다고. 좁은 자동화(코드 리뷰·영향 분석)는 개별 단계를 빠르게 했지만 전체 사이클은 못 닫았다. Codey는 그 간극을 메우려고 설계됐다.

🔧 하네스 관점
reviewer와 verifier를 분리한 6역할 구조가 네 듀얼 검수(ui/code)와 공명한다. 역할별 모델 차등(비싼 모델은 판단에, 싼 모델은 실행에)도 네 하네스의 비용 구조 설계에 직접 참고할 만하다.

볼 포인트 ─ 75%의 분모(작업 난이도 분포), 실패 25%의 유형.
