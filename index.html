Claude Duet… "말 걸면 일하는" 상시 에이전트
Anthropic 발표 (10월 21일) · 9to5Mac · Herald Business (10월 22~23일)

Anthropic이 Claude Duet 연구 프리뷰를 공개했다. 질문을 기다리는 챗봇이 아니라, 연결된 앱을 스스로 살피고 아침 브리핑을 가져오며, 위임받은 일을 백그라운드에서 계속하는 에이전트다. 자체 클라우드 가상 컴퓨터에서 돌아가 앱을 닫아도 일이 계속된다. 모델은 Claude Opus 5.5, 커넥터는 6,000개 이상(Gmail·Slack·Stripe·Shopify·Notion 등). 미국 Pro·Max 구독자 대상 대기자 명단 순차 초대, Team·Enterprise는 아직 제외다.

안전 장치가 설계의 핵심이다. 메시지 발송·결제·서명·삭제 전에는 반드시 사용자 확인을 거치고, 증권 거래·계좌 간 송금은 승인해도 금지한다. 발신 내용에서 민감정보 유출을 걸러내는 분류기도 새로 내놨다. 단, 백그라운드 작업도 플랜 사용량에 포함돼 한도가 더 빨리 닳는다. Anthropic 스스로 "스레드를 오독하거나 긴급도를 잘못 잴 수 있다"고 인정했다.

🔧 하네스 관점
Duet의 승인 게이트 설계는 네 하네스의 리뷰어 권한 규칙과 같은 문법이다. '확인 전 금지 동작 목록 + 승인해도 금지 동작 목록'의 이중 구조를 하네스 문서에 명문화하면, 리뷰어·에이전트 역할별 권한표로 바로 쓸 수 있다. 백그라운드 작업의 사용량 계상도 하네스 운영 비용 설계에 참고할 점이다.

볼 포인트 ─ Team·Enterprise 확대 시기, 한국 출시 여부.

OpenAI Decisions API 정식 출시… 150ms의 "선택" 엔드포인트
OpenAI (10월 22일 GA) · AI Weekly · EconoTimes (10월 23~24일)

OpenAI가 Decisions API를 정식 출시했다. 자유 텍스트를 생성하지 않고, 개발자가 정한 질문에 정해진 답 중 하나를 돌려주는 엔드포인트다. POST /v1/decisions, 모델은 GPT-6 Luna 전용. 질문 유형은 확률을 내는 predicate, 목록에서 고르는 choice, 순서형 루브릭으로 매기는 score 세 가지. 요청당 최대 400문항(베타 200문항에서 상향), 가격은 입력 토큰 100만 개당 $0.10, 캐시 $0.01, 출력 무료다.

핵심은 속도다. 기존 1~3초짜리 호출이 100~180ms로 줄었다. OpenAI는 "Responses API 대비 약 10배"라 하고, 다음 목표는 60ms — "비디오의 매 프레임마다 API 호출"이 가능한 수준이다. 경쟁 구도가 선명하다. 이 카테고리를 만든 TypeSafe의 Jev는 수주 만에 기업가치 $7.6B가 됐고, OpenAI는 DevDay 프리뷰에서 23일 만에 GA로 밀어붙였다. 초기 고객 Speak는 액션 간 지연을 1.4초에서 0.13초로 줄였다.

🔧 하네스 관점
네 하네스의 리뷰어 판정(PASS/BLOCK/INCONCLUSIVE)이야말로 Decisions API의 천생 용도다. 자유 텍스트 판정을 파싱하는 대신 predicate(위반 확률)·choice(판정)·score(심각도)로 받으면, 리뷰 결과의 기계 판독성과 비용이 동시에 좋아진다. 다만 주의할 점: 결정 모델은 별도 학습 모델이 아니라 Luna를 재구성한 것이다. 판정 품질은 결국 네가 주는 답안 공간(라벨 집합)의 설계에 달려 있다.

에이전트가 git을 부쉈다… Anthropic, 버전 관리 자체를 교체
Flowtivity 분석 (10월 15일)

Anthropic 내부 코딩 에이전트의 병합량이 2026년 5월 하루 2,500건에서 9월 3만 건으로 12배 뛰면서, 인간 규모로 설계된 git이 병목이 됐다. 7명의 엔지니어가 5개월 만에 Scion이라는 사내 버전 관리 시스템을 만들고 모노레포를 git에서 완전히 이주시켰다. 모든 커밋·리베이스·병합이 서버에서 일어나고, 체크아웃은 희소·가상화되며, blame·이력은 API로 답한다. 결과: 변경당 소스 관리 시간 34분에서 3.7분으로 9.2배 단축, 인프라 규모 200분의 1, CI CPU 용량 25% 확보.

교훈은 분명하다. 에이전트 시대의 병목은 모델이 아니라 인간용 도구다. 멀티 에이전트 워크플로우가 3~10배 토큰을 먹는다는 비용 문제와 함께, 버전 관리·CI·리뷰 파이프라인 전체가 에이전트 규모를 전제로 다시 설계돼야 한다. 참고로 구글의 동명 오픈소스 오케스트레이션 테스트베드(google-deepmind/scion)와는 다른 시스템이다. 이름이 같아 헷갈리기 쉽다.

🔧 하네스 관점
네 하네스의 듀얼 리뷰어 구조도 같은 질문을 받게 된다. 에이전트 병합량이 10배가 되면 리뷰 큐·증거 수집·before/after 이미지 검증이 어디서 터지는가. Scion의 답은 '인프라를 에이전트 규모로 바꾸는 것'이었다. 하네스에도 리뷰 요청의 우선순위 큐와 자동 증거 수집(브라우저 조작 결과 자동 캡처) 같은 설계가 필요하다.
